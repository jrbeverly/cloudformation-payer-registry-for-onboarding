# AWS Organization Onboarding

## Vision

Explore a self-registering onboarding flow for bringing an existing AWS Organization under centralized management.

The primary scenario is a merger, acquisition, or other organizational change where a company inherits an AWS environment that already exists independently.

The goal is not to immediately rebuild that environment or force it into a predefined structure.

The goal is to establish an initial trust relationship, discover what exists, and create enough access for the company's normal infrastructure-management systems to begin taking ownership of the environment.

The onboarding experience should be simple for the team responsible for the incoming AWS estate:

> deploy this CloudFormation stack

From that point onward, the process should be capable of continuing automatically.

## Problem

Acquired AWS environments may contain:

- one or more AWS Organizations;
- existing management accounts;
- many member accounts;
- existing IAM relationships;
- established networking;
- resources that need to remain in place;
- and infrastructure that was created outside the acquiring company's Terraform or deployment systems.

The environment cannot reasonably be treated like a new AWS account.

It first needs to be discovered and progressively incorporated into the existing management model.

Before any of that can happen, however, the central platform needs a trusted way to access the new environment.

A purely manual onboarding process might involve:

1. creating an IAM role;
2. copying its ARN;
3. recording account identifiers;
4. manually entering those values into another system;
5. configuring permissions;
6. and then starting discovery.

This project should explore whether that initial handoff can be reduced to a single bootstrap deployment followed by automatic self-registration.

## Bootstrap Artefact

Provide the incoming organization with a CloudFormation stack.

Initially, this can simply be generated by a script.

There is no requirement to build a full onboarding portal or user interface before the underlying flow has been demonstrated.

A future system could generate the stack from a backend service or form, but the paper prototype only needs to show that the resulting CloudFormation artefact can carry enough context to bootstrap the process.

Conceptually:

> generate onboarding stack
> → give stack to incoming organization
> → deploy into AWS management account

The generated stack becomes the initial onboarding package.

## Bootstrap Role

The primary responsibility of the stack is to create an IAM role that the central management system can assume.

This role is not intended to become the final permanent deployment architecture.

Its purpose is bootstrap.

At its simplest, it is effectively a:

> role deployer

Once the central platform can assume this role, it can begin establishing the additional roles and resources needed for normal operation.

Those might eventually include:

- Terraform deployment roles;
- organization discovery roles;
- account-specific roles;
- networking resources;
- prefix lists;
- inventory collectors;
- integration resources;
- or other infrastructure required by the company's platform.

The initial role only needs enough capability to safely enable the next stage.

## Self-Registration

The CloudFormation deployment should not end with:

> the role now exists; copy the ARN somewhere.

Instead, the stack should notify the central platform that the bootstrap operation has completed.

Conceptually:

> stack deployed
> → role created
> → registration event emitted
> → central platform receives registration
> → onboarding starts

This is the core behaviour the project should demonstrate.

The exact notification transport is deliberately open.

Possible mechanisms include:

- an API call;
- EventBridge;
- SQS;
- SNS;
- or another simple event or messaging mechanism.

The important property is not which AWS service is used.

The important property is:

> the newly bootstrapped environment tells the central platform that it exists and is ready.

## Registration Information

The registration event should carry enough information for the central system to identify the environment and begin interacting with it.

Useful information may include:

- AWS account identifier;
- AWS Organization identifier;
- bootstrap role ARN or predictable role information;
- an onboarding request identifier;
- organization or business metadata;
- deployment region;
- or other minimal context required to correlate the registration with the original onboarding request.

The exact schema should emerge from the implementation.

Avoid putting unnecessary information into the registration message simply because it may be useful later.

The message should contain enough to begin the next step.

## Event-Driven Handoff

The registration event marks the transition between two different systems.

Before registration:

> the incoming organization owns the action

They deploy the supplied stack.

After registration:

> the central platform owns the action

It can now assume the bootstrap role and begin onboarding.

This removes the need for a manual coordination step between deployment and discovery.

The useful abstraction is:

> human-triggered bootstrap → machine-driven onboarding

That transition is one of the main things this prototype should explore.

## Discovery

Once access has been established, the central platform can begin inspecting the AWS environment.

Initial discovery may include:

- organization structure;
- organizational units;
- member accounts;
- account metadata;
- existing IAM roles;
- networking configuration;
- VPCs;
- route tables;
- CIDR allocations;
- existing shared infrastructure;
- and other resources relevant to subsequent onboarding.

The exact discovery scope does not need to be exhaustive.

The initial prototype only needs enough discovery to prove that the central system can successfully enter the acquired environment and begin understanding it.

## Progressive Management

The acquired estate already exists.

The purpose of onboarding is therefore not simply to deploy new infrastructure.

It is to progressively move existing infrastructure into the company's normal management model.

That may involve:

- identifying existing resources;
- determining which resources should remain untouched;
- importing selected resources into Terraform;
- deploying missing standard components;
- creating deployment roles;
- introducing standard networking;
- and gradually replacing ad hoc management with normal platform workflows.

This project does not need to solve that full lifecycle.

It should establish the bootstrap point from which those processes become possible.

## Terraform Integration

One important downstream use of the bootstrap role is enabling the existing Terraform environment to interact with the acquired AWS estate.

The platform should eventually be able to:

1. discover existing resources;
2. determine which resources correspond to managed Terraform concepts;
3. import or represent those resources;
4. deploy additional required infrastructure;
5. and transition the environment into normal management.

The prototype does not need to automate every Terraform import.

It should demonstrate that the onboarding mechanism provides sufficient access and information for those workflows to begin.

## Generated Stacks

The onboarding CloudFormation template may be generated specifically for a particular onboarding request.

This allows the stack to contain information that helps the central platform correlate the eventual registration event.

For example:

> onboarding request
> → generate stack containing registration context
> → stack deployed
> → registration returns that context

The initial implementation can use a command-line script to generate the template.

That is sufficient.

Avoid building a complete web application merely to make the stack generation process look polished.

The important experiment is the onboarding protocol.

## Trust Bootstrap

The project should make the trust relationship explicit.

There are two initially separate environments:

> central management environment

and:

> acquired AWS environment

The CloudFormation stack is the mechanism by which the acquired environment explicitly authorizes the central environment to begin interacting with it.

That makes the deployment itself a useful trust ceremony.

The project should explore how little initial configuration is required to establish that trust while still making the flow understandable.

## Failure and Retry

Because the process crosses systems, explore what happens when only part of the flow succeeds.

Examples include:

- CloudFormation succeeds but registration fails;
- registration succeeds but the central system cannot assume the role;
- the registration event is delivered more than once;
- the central onboarding process fails partway through;
- the stack is deployed again;
- or onboarding is restarted.

The paper prototype does not need sophisticated recovery orchestration.

It should, however, avoid designs where one transient failure requires rebuilding the entire environment manually.

Idempotent registration and restartable onboarding are useful properties to explore.

## Questions

The project should help answer questions such as:

- What is the minimum infrastructure required to bootstrap an acquired AWS Organization?
- What permissions does the initial bootstrap role actually require?
- Can the initial role remain narrowly focused on deploying the permanent management roles?
- What information should be embedded into the generated CloudFormation stack?
- What information needs to be sent back during registration?
- What is the simplest useful registration mechanism?
- Should registration be synchronous or event-driven?
- How should duplicate registration events behave?
- How does the central system verify that the reported role and account belong to the expected onboarding request?
- What organization information can be discovered immediately after bootstrap?
- Which resources can be brought directly into existing Terraform workflows?
- Which parts of onboarding require dedicated transition logic?
- When can the bootstrap role be reduced, replaced, or removed?
- What happens if an onboarding attempt must be restarted?
- How much of the process can occur without manual copying of AWS identifiers?

These questions should guide experimentation rather than imply a fixed architecture.

## Boundaries

Do not attempt to solve the entire merger-and-acquisition integration lifecycle.

The initial project does not need to:

- migrate every AWS resource;
- automatically import an entire organization into Terraform;
- standardize every account;
- redesign inherited networking;
- enforce every security control;
- build a complete onboarding portal;
- or automate every organizational policy.

Those are downstream concerns.

The core prototype should remain focused on:

> establish trust → self-register → discover → begin management

Likewise, avoid prematurely building a generalized onboarding product for every possible AWS architecture.

The first implementation only needs to demonstrate the pattern convincingly.

## Expected Output

The repository should demonstrate the complete bootstrap and registration cycle.

Useful outputs may include:

- a simple onboarding-stack generator;
- a generated CloudFormation template;
- a bootstrap IAM role;
- a registration mechanism;
- a central receiver for registration events;
- role assumption from the central environment;
- initial AWS Organization discovery;
- and a small demonstration of subsequent management or Terraform-oriented activity.

The project should retain enough information to make the lifecycle easy to understand.

A successful demonstration should make it clear which actions happen:

- before the stack is deployed;
- during deployment;
- during registration;
- after the central system receives the event;
- and when normal management begins.

## Success

The work is successful if onboarding a previously unmanaged AWS Organization can begin with a simple instruction:

> deploy this CloudFormation stack into the management account.

After that deployment, the central system should learn that the environment exists, obtain the information required to access it, assume the bootstrap role, and begin discovery without requiring someone to manually copy role ARNs or account metadata between systems.

The key question is:

> Can an acquired AWS environment bootstrap its own transition into centralized management?

The paper prototype should demonstrate that event-driven handoff clearly enough to inform a more durable implementation later.
